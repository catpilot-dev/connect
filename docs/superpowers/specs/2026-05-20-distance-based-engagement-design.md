# Distance-Based Engagement Metric

**Date:** 2026-05-20
**Status:** Design approved, awaiting implementation plan

## Problem

`engagement_pct` in COD is currently time-based: the fraction of route duration in which `selfdriveState.enabled` is true. Two issues:

1. **Idle inflates total_ms.** Stopped at a light with openpilot off still counts against you; same time with openpilot engaged still counts for you. The metric drifts toward "how often the system was on" rather than "how much driving the system did."
2. **Trailing segment is rounded up to a full minute.** `total_ms = (maxqlog + 1) × 60_000`. A 90s route reports 120_000 ms, capping engagement at 75% even with the system on the whole time.

Distance-based engagement (engaged_meters / total_meters) addresses both: idle weight is naturally zero, and total comes from GPS-measured route distance rather than nominal segment count.

## Decision Summary

| Question                                          | Decision                                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Per-route metric                                  | Replace `engagement_pct` semantics with distance-based, no time-based fallback |
| Aggregate stats in `/v1.1/devices/{id}/stats`     | Replace `engaged_minutes` / `total_minutes_with_events` with miles equivalents |
| Data source                                       | Cached `coords.json` (already generated at enrichment)                         |
| Behavior when coords absent                       | Hide `engagement_pct` (same as today's behavior when events absent)            |

## Architecture

### Data sources (existing, no new pipeline)

- **`events.json`** per segment — already cached at enrichment. `type=="state"` entries carry `data.enabled` and `route_offset_millis`.
- **`coords.json`** per segment — already cached at enrichment. Each entry: `{t: seconds (route-relative), dist: meters (per-segment cumulative), lat, lng}`.
- Both files co-generated by `rlog_parser._generate_events_json` and `rlog_parser._generate_coords_json` during enrichment; gated by `meta.enriched` in route_store.

### New function: `_route_engaged_distance(store, route) -> (engaged_m, total_m)`

Location: `route_helpers.py`, replacing `_route_engagement`.

```
1. For each segment in route._segments (sorted by number):
     load coords.json; if missing → return (0, 0)
     load events.json; if missing → return (0, 0)

2. Build route-wide arrays:
     t_ms[]   — coords[*].t × 1000  (already route-relative seconds → ms)
     cum_m[]  — coords[*].dist rebased: add prior segment's last dist as offset
              (per-segment dist resets to 0; we want cumulative across route)

3. Collect engagement intervals from events.json (state events only):
     walk events in order; on rising edge enabled=true record on_ms;
     on falling edge enabled=false record (on_ms, off_ms) pair, reset on_ms;
     if still on at end of last segment, close at t_ms[-1].

4. For each (on_ms, off_ms) pair:
     dist_on  = linear-interp cum_m at on_ms  (bisect_left + blend)
     dist_off = linear-interp cum_m at off_ms
     engaged_m += dist_off - dist_on

5. total_m = cum_m[-1]
   return (engaged_m, total_m)
```

Numpy is not currently a COD runtime dep — use `bisect_left` plus an inline two-point linear blend. Out-of-range offsets clamp to first/last `cum_m`.

### Per-route engagement_pct (`handlers/routes.py`)

`handlers/routes.py:228-234` currently does:
```python
if meta.get("engagement_pct") is None:
    engaged_ms, total_ms = _route_engagement(store, route)
    if total_ms > 0 and engaged_ms > 0:
        meta["engagement_pct"] = round(engaged_ms / total_ms * 100)
```

Replaced with:
```python
if meta.get("engagement_metric_version") != 2 or meta.get("engagement_pct") is None:
    engaged_m, total_m = _route_engaged_distance(store, route)
    if total_m > 0:
        meta["engagement_pct"] = round(engaged_m / total_m * 100)
        meta["engagement_metric_version"] = 2
        store._rebuild_routes()
        store._save_metadata()
        route = store.get_route(route_name)
```

The `engagement_metric_version` key handles migration: routes with legacy time-based values get recomputed on next view. `engaged_m == 0 and total_m > 0` is valid (drove the route, never engaged) → percent is written as 0, not skipped.

### Aggregate stats (`handlers/auth.py`)

Current keys:
- `engaged_minutes`         → renamed to `engaged_miles`
- `total_minutes_with_events` → renamed to `total_miles_with_engagement`

Both populated by summing `_route_engaged_distance` results across routes (m → mi via `/ 1609.344`). `distance`, `minutes`, `routes` fields unchanged.

This is a **breaking API change** to `/v1.1/devices/{id}/stats`. Per the design decision, no compatibility shim is added.

### Frontend

`RouteCard.svelte:140-142` reads `route.engagement_pct` as a percent — display unchanged.

`derived.js:83-94` (`calculateEngagement` from frontend-visible timeline events) is parallel logic used by the detail page. Out of scope for this change — its inputs are sparse timeline events, not GPS, so it stays time-based. Acceptable mismatch: card percent is route-level summary (distance-based), detail page is event-level inspector (time-based). Documented in API.md.

## API Changes

### `/v1.1/devices/{id}/stats`

Before:
```json
{"all":  {"distance": 1234.5, "minutes": 420, "routes": 15,
           "engaged_minutes": 280.3, "total_minutes_with_events": 350.0}}
```

After:
```json
{"all":  {"distance": 1234.5, "minutes": 420, "routes": 15,
           "engaged_miles": 1050.2, "total_miles_with_engagement": 1234.5}}
```

`API.md` updated to reflect new fields and note distance-based semantics.

### Route metadata

Adds one persistent key on the route metadata entry: `engagement_metric_version: 2`. Used only for migration; not exposed via the API.

`engagement_pct` retains its name and shape (integer percent); only its computation changes.

## Tests

### `tests/test_route_helpers.py`
Replace existing `_route_engagement` cases with `_route_engaged_distance` covering:

1. **No coords cache** → returns `(0, 0)`.
2. **No events cache** → returns `(0, 0)`.
3. **Single engagement, single segment** — coords at `[(0,0), (30,500), (60,1000)]`, engaged from t=10000 to t=50000. Expected engaged_m = interp(50_000)-interp(10_000) = 833.3-166.7 = 666.6.
4. **Engagement spanning segment boundary** — two segments, engaged from seg0 t=40_000 to seg1 t=20_000 (= route ms 80_000). Per-segment dist rebases correctly.
5. **Open engagement at route end** — engaged at last event, closes at `t_ms[-1]`, not at `(seg+1)*60_000`.
6. **Stopped while engaged (idle)** — coords stationary across engaged window → engaged_m = 0 even though duration > 0. This is the key behavioral change.

- Update any aggregate-field assertions for `engaged_miles` / `total_miles_with_engagement` rename.
- Migration test: route with stale `engagement_pct` and no `engagement_metric_version` recomputes when viewed.

### Stats endpoint test
- Verify response shape matches new field names; verify aggregation across mixed routes (some with coords, some without).

## Migration

- On first view of any existing route, `engagement_metric_version != 2` triggers a fresh distance-based compute. Routes are recomputed lazily as users browse. No batch backfill — keeps the change minimal and avoids long startup.
- The aggregate stats endpoint recomputes from `_route_engaged_distance` every call (it already loops all routes), so the rename is effective immediately on deploy.

## Out of Scope (YAGNI)

- **vEgo integration** — would give engagement at sub-GPS-rate resolution but requires extending events.json schema. Not justified for the precision gain.
- **Backfilling aggregates on startup** — lazy migration is fine.
- **Compat shim for old field names** — explicit clean break.
- **Frontend detail-page timeline rewrite** to use distance — event-level inspector serves a different purpose; mismatch with card is acceptable.
- **Cat-eye (RK3588) device** — independent of this metric change.

## Risks

- **Stale `engagement_pct` between deploys**: if a user views a route on the old version, then upgrades, the cached value is wrong until they revisit. Acceptable — solved by the version bump.
- **Coords.json with sparse GPS**: a route with only a few fixes will have crude interpolation, but the total also comes from the same source so the ratio remains meaningful.
- **External clients consuming the stats endpoint** break silently. The user is the only consumer; documented break is acceptable.
